# 013 — Server drafts, uploads, previews and browser approval

Date: 2026-10-08. Status: owner-authorized implementation; merged to main at 15:49 -0400 in `b9bd1f8` and `6ff79db`. Successful production rollout remains unverified after the public health HTTP 503 at 16:46:22 -0400. Supersedes the initial intake/approval workflow in decisions 007 and 009. Historical policy/contract artifacts remain frozen.

## Decision

Policy **2.0.0**, site contract **2.0**, and append-only migration **007** replace client-made preview submissions. Both `SITE_WORKFLOW_ENABLED` and default-false `SITE_DRAFTS_ENABLED` are required. The client's LLM incrementally supplies catalog content. The platform stores revisions, normalizes out-of-band images, assembles complete specs, builds immutable snapshots, verifies them, obtains scoped browser approval, and deploys the stored artifact. The entire canonical spec is hashed; approval is a separate immutable record.

Draft operations use stable IDs, explicit insertion positions, atomic batches of at most 32 operations/64 KiB, optimistic revision checks, and actor/request idempotency receipts. Supplied values must satisfy catalog rules and aggregate budgets; incomplete content and forward references are preview blockers. Summaries are at most 4 KiB, asset lists paginate, and errors are capped at 20. Existing catalog ownership, scoped administrators, testers, CMS password encryption, explicit deployment confirmation and operation history remain.

Shared one-hour upload sessions expose a human URL/locally generated QR and a narrowly scoped 256-bit bearer capability. The capability is a cryptographic pseudorandom HMAC output over a random session identifier and the controller secret, which permits identical idempotent open responses while persisting only its hash. It grants one-byte probe/upload rights, never approval. Use agent HTTP only with file and HTTP access after a three-second probe; otherwise show the human link/QR and wait. Browser uploads require verified Google identity, owner or enabled site membership, exact Origin and session-bound CSRF. No image bytes, base64 or remote image URLs enter MCP.

Decode JPEG/PNG/static WebP in a separate secret-free child, one decoder globally, 10-second kill deadline, bounded stdin/stdout, disabled Sharp cache. Reject animation, malformed/unsupported input, over 20 MiB, 40 MP or 12,000 px/side. Fully decode, orient, preserve transparency/aspect ratio, strip metadata, never upscale. Recipe `1.0.0` tries edges 2560/2048/1536/1024 with quality 80/70/60, choosing the first output within 2 MiB. Metadata and hashes come only from normalized WebP output. Originals are discarded. The controller independently rechecks output hashes and bounded WebP headers; subsequent server generation uses those normalized records without invoking a native decoder in the credential-bearing process. Existing 50-image/25 MiB draft limits remain.

Admission limits: three drafts/owner, 50 globally; seven idle/30 absolute days; one session/draft, three/owner; 100 MiB raw/100 attempts/session; 200 MiB raw/owner and 1 GiB globally per rolling day. Verification allows five new attempts/owner and 25 globally per rolling day, one active job globally. Failed attempts count. Canonical content plus generator, policy and checker provenance scope deduplication to the same owner/test classification; pending/cached copies consume no further admission and never copy an approval.

Snapshots progress `queued → building → verified → approved → deploying → live`, with failed, superseded and unknown outcomes. Retain at most three artifact-bearing snapshots/draft; expire unapproved artifacts after 24 hours and approved undeployed artifacts after seven days. Deployments use existing site retention. Persistent prefix write intents make interrupted bucket writes discoverable; bounded cleanup resumes after failure, protects live/unknown artifacts and audit/approval history, and tester reset covers draft and spec prefixes.

## Approval and preview threat models

The client, its files and all rendered content are untrusted data. A short URL proves no membership. A leaked capability can spend only its bounded session upload quota until expiry/revocation; it cannot read private platform state or approve/deploy. Capability authentication precedes large body reads. Exact Origin and cookie/session-bound CSRF protect browser mutations. Approval additionally consumes a single-use session/snapshot nonce, rechecks verified identity and current owner/scoped membership, and records actor/time/revision/spec/output hashes. Global roles alone grant no approval. No MCP or bearer-only approval route exists.

Preview tokens are snapshot-scoped, signed and expire in 15 minutes. Relative paths preserve identical root-deployed bytes. The iframe and response header both sandbox without scripts or same-origin permission; only the signed path may load CSS/images/fonts. Forms, connections, workers, popups and top navigation are unavailable. Cookie-independent preview handlers set no cookies and emit no-store, no-referrer, nosniff and noindex. Direct opening receives the same header sandbox. Screenshot/report hashes are recorded and checked against storage; required screenshots cover every page at 390/1280 px. Failed reports/screenshots remain reviewable, with approval disabled.

Site row locks serialize edit, approval and deploy admission. Edits supersede snapshots; reverting never revives approval. Queued/running/unknown deployment freezes mutations. Both admission and worker verify current revision, approver membership, tester classification, spec/source/output and artifact integrity. Deployment reads verified files without generation/normalization/rebuild. Uncertain provider outcomes remain unknown for explicit reconciliation.

## Rejected alternatives and release gates

Rejected: client approval assertions and preview bundles (no trustworthy browser authorization); parity against client previews (wrong ownership of production); inline MCP image/base64 transport (context/body exposure); remote image fetching (SSRF/unclear provenance); bearer approval (human authorization bypass); in-process decoding (secret/process exposure); unconstrained encoders/provider retries (cost and resource uncertainty); a parallel legacy workflow (ambiguous contracts). Thumbnail MCP tooling and draft-based change requests are deferred. `change.request` returns `change_requests_unavailable`; live sites cannot redeploy through initial drafts.

Migrations 001–006 are byte-for-byte preserved. Production's earlier 006 was reconciled by the owner to the current file on 2026-10-07 (owner-reported; see [release evidence](../release-verification.md#hosted-catalog-activation--2026-10-07-to-2026-10-08-owner--and-agent-reported)); migration 007 is now on main, but its production application is unverified after the observed HTTP 503. No production activation, variables, DNS, payments, merge or deployment is authorized. One isolated hosted tester fixture is the explicit exception; its fictional approval session does not verify real Google authentication. Observed results, cleanup and unavailable billing values belong in release evidence, not inferred from a successful build or PR.
